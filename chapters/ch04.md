# Chapter 4 — How to Create Reusable Infrastructure with Terraform Modules

## Core Idea
Modules are the primary unit of code reuse and encapsulation in Terraform. Any directory containing `.tf` files is a module. The directory where `terraform apply` is executed is the **root module**; any module referenced via a `module` block is a **child module**. Production modules must be small, composable, explicitly parameterized, and version-pinned.

---

## Frameworks Introduced

### 1. Standard Module Directory Structure
```
modules/
└── services/
    └── web-cluster/
        ├── main.tf          # Core infrastructure resources (ASG, ALB, SGs)
        ├── variables.tf     # Input variables (configurable parameters)
        ├── outputs.tf       # Exported attributes (usable by root module)
        ├── user_data.sh.tpl # Bootstrap scripts
        └── README.md        # Usage documentation and requirements
```

### 2. Module Communication Mechanics
- **Inputs**: Defined as `variable` blocks in the child module; passed as attributes in the caller's `module` block.
- **Outputs**: Defined as `output` blocks in the child module; accessed in the caller module via `module.<MODULE_NAME>.<OUTPUT_NAME>`.
- **Locals**: Intermediate variables scoped strictly *inside* the child module; inaccessible to external caller modules.

### 3. The Path Resolution Framework (`path` Expressions)
When referencing local files or scripts within a child module:
- `path.module`: Filesystem path to the *child module* folder where the expression is defined (Always use this for loading files inside modules).
- `path.root`: Filesystem path to the *root module* where `terraform apply` was executed.
- `path.cwd`: Current working directory where Terraform was invoked.

### 4. Inline Blocks vs. Standalone Resources Rule
Certain AWS resources support embedded configuration blocks (e.g. `ingress` inside `aws_security_group`, `route` inside `aws_route_table`) OR separate standalone resource blocks (`aws_security_group_rule`, `aws_route`).
- **Golden Rule**: **Always standardize on standalone resource blocks when writing reusable modules.**
- *Why*: Inline blocks lock down configuration inside the module; standalone resource blocks allow callers to add custom security group rules or routes without modifying module source code. Never mix both.

## Code Examples

### 1. Child Module Variable Definition (`modules/services/web-cluster/variables.tf`)
```hcl
variable "cluster_name" {
  description = "The name to use for all resources in this cluster"
  type        = string
}

variable "db_remote_state_bucket" {
  description = "The name of the S3 bucket for the database's remote state"
  type        = string
}

variable "db_remote_state_key" {
  description = "The path in the S3 bucket for the database's remote state"
  type        = string
}

variable "instance_type" {
  description = "The type of EC2 Instances to run (e.g. t3.micro)"
  type        = string
  default     = "t3.micro"
}

variable "min_size" {
  description = "Minimum number of EC2 instances in the ASG"
  type        = number
}

variable "max_size" {
  description = "Maximum number of EC2 instances in the ASG"
  type        = number
}
```

### 2. Child Module Implementation (`modules/services/web-cluster/main.tf`)
```hcl
locals {
  http_port    = 80
  any_port     = 0
  any_protocol = "-1"
  tcp_protocol = "tcp"
  all_ips      = ["0.0.0.0/0"]
}

data "terraform_remote_state" "db" {
  backend = "s3"

  config = {
    bucket = var.db_remote_state_bucket
    key    = var.db_remote_state_key
    region = "us-east-2"
  }
}

resource "aws_launch_template" "example" {
  name_prefix   = "${var.cluster_name}-lt-"
  image_id      = "ami-0fb653ca2d3203ac1"
  instance_type = var.instance_type

  vpc_security_group_ids = [aws_security_group.instance.id]

  # Always resolve file relative to path.module
  user_data = base64encode(templatefile("${path.module}/user_data.sh.tpl", {
    server_port = local.http_port
    db_address  = data.terraform_remote_state.db.outputs.address
    db_port     = data.terraform_remote_state.db.outputs.port
  }))

  lifecycle {
    create_before_destroy = true
  }
}

resource "aws_autoscaling_group" "example" {
  name_prefix         = "${var.cluster_name}-asg-"
  min_size            = var.min_size
  max_size            = var.max_size
  vpc_zone_identifier = data.aws_subnets.default.ids

  launch_template {
    id      = aws_launch_template.example.id
    version = "$Latest"
  }

  lifecycle {
    create_before_destroy = true
  }
}

# Standalone Security Group and Rules
resource "aws_security_group" "instance" {
  name_prefix = "${var.cluster_name}-instance-sg"
}

resource "aws_security_group_rule" "allow_http_inbound" {
  type              = "ingress"
  security_group_id = aws_security_group.instance.id
  from_port         = local.http_port
  to_port           = local.http_port
  protocol          = local.tcp_protocol
  cidr_blocks       = local.all_ips
}
```

### 3. Child Module Outputs (`modules/services/web-cluster/outputs.tf`)
```hcl
output "asg_name" {
  value       = aws_autoscaling_group.example.name
  description = "The name of the Auto Scaling Group"
}

output "instance_security_group_id" {
  value       = aws_security_group.instance.id
  description = "The ID of the EC2 Instance Security Group"
}
```

### 4. Root Module Invocation (`stage/services/web-cluster/main.tf`)
```hcl
module "web_cluster" {
  source = "../../../../modules/services/web-cluster"

  cluster_name           = "web-cluster-stage"
  db_remote_state_bucket = "my-company-tf-state-prod"
  db_remote_state_key    = "stage/data-stores/mysql/terraform.tfstate"
  instance_type          = "t3.micro"
  min_size               = 2
  max_size               = 4
}

# Extending module functionality from root module using standalone resources
resource "aws_security_group_rule" "allow_testing_custom_port" {
  type              = "ingress"
  security_group_id = module.web_cluster.instance_security_group_id
  from_port         = 9090
  to_port           = 9090
  protocol          = "tcp"
  cidr_blocks       = ["10.0.0.0/16"]
}
```

## Anti-patterns

- **Hardcoding Relative File Paths (`file("script.sh")`)**:
  - *Why it fails*: `file()` resolves relative to the working directory where `terraform apply` is executed, NOT where the module file lives. Fails when invoked from different root directories. **Fix**: Use `${path.module}/script.sh`.
- **Mixing Inline Blocks and Standalone Resources**:
  - *Why it fails*: Terraform will conflict and continuously overwrite rules or routes on subsequent runs if both inline `ingress {}` blocks and `aws_security_group_rule` resources target the same SG.
- **Deeply Nested Module Hierarchies (Module Multi-layering)**:
  - *Why it fails*: Nesting modules 4-5 levels deep makes tracking variable pass-through nightmare fuel, inflates plan execution times, and makes debugging impossible. Keep nesting to a maximum of 1-2 levels.

---

## Key Takeaways

1. **Modules Must Be Self-Contained**: Pass all parameters via `variable` blocks and export all needed values via `output` blocks.
2. **Always Use `path.module`**: Qualify file references inside child modules using `${path.module}`.
3. **Prefer Standalone Resources**: Use standalone rule/route resources to allow caller extensibility.
4. **Document Every Variable & Output**: Always include clear `description` strings in `variables.tf` and `outputs.tf`.
