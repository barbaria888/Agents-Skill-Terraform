# Chapter 8 — Production-Grade Terraform Code: Refactoring, Versioning, and Releases

## Core Idea
Production-grade Terraform requires treating infrastructure code with the same rigor as application software. This includes pinning remote module releases to immutable version tags, maintaining the dependency lock file (`.terraform.lock.hcl`), enforcing safety checks, and using declarative HCL refactoring blocks (`moved`, `import`, `check`, `removed`) instead of manual, destructive state manipulation.

---

## Frameworks Introduced

### 1. The Declarative Refactoring Framework

| HCL Block | Version | Purpose | Replaces Manual Workaround |
|---|---|---|---|
| **`moved`** | TF 1.1+ | Refactor/rename resources or move resources into modules in code without destroying assets | `terraform state mv` |
| **`import`** | TF 1.5+ | Declaratively import existing "brownfield" infrastructure into state via HCL code | `terraform import` CLI |
| **`check`** | TF 1.5+ | Perform continuous, non-blocking operational health assertions post-deployment | Custom monitoring scripts |
| **`removed`** | TF 1.7+ | Declaratively remove resources from state management without destroying underlying assets | `terraform state rm` |

### 2. Module Repository Layout Frameworks
- **Monorepo (One Repo, Many Modules)**:
  - *Source URL*: `github.com/org/terraform-modules//services/web-cluster?ref=v1.2.0`
  - *Trade-off*: Easy cross-module maintenance, but single git release tag versions all modules simultaneously.
- **Multi-Repo (One Repo Per Module)**:
  - *Source URL*: `github.com/org/terraform-aws-web-cluster?ref=v1.2.0`
  - *Trade-off*: Strict semantic versioning (`v1.0.0`) per module, but high PR maintenance overhead across repositories.

### 3. The Provider Lock File Framework (`.terraform.lock.hcl`)
- Tracks exact checksums (hashes) and version numbers of compiled provider binaries downloaded during `terraform init`.
- **Golden Rule**: **Always commit `.terraform.lock.hcl` to Git version control.** Ensures every team member and CI runner executes against identical, verified provider binaries.

## Code Examples

### 1. Safe Refactoring with `moved` Blocks (`main.tf`)
```hcl
# Scenario A: Renaming a resource identifier
moved {
  from = aws_instance.web_server
  to   = aws_instance.web_app
}

# Scenario B: Moving a resource into a child module
moved {
  from = aws_security_group.alb
  to   = module.web_cluster.aws_security_group.alb
}

# Scenario C: Refactoring count (list) to for_each (map)
moved {
  from = aws_iam_user.users[0]
  to   = aws_iam_user.users["alice"]
}
moved {
  from = aws_iam_user.users[1]
  to   = aws_iam_user.users["bob"]
}
```

### 2. Declarative Brownfield Onboarding with `import` Blocks (`import.tf`)
```hcl
# 1. Declare the import target
import {
  to = aws_s3_bucket.legacy_data
  id = "my-company-legacy-bucket-2019"
}

# 2. Run: terraform plan -generate-config-out=generated.tf
# 3. Terraform automatically generates the resource block:
resource "aws_s3_bucket" "legacy_data" {
  bucket        = "my-company-legacy-bucket-2019"
  force_destroy = false
}
```

### 3. Non-Blocking Operational Checks with `check` Blocks (`check.tf`)
```hcl
# Validate that the deployed web endpoint returns HTTP 200 without failing deployment
check "web_health" {
  data "http" "endpoint" {
    url = "https://${aws_lb.example.dns_name}/health"
  }

  assert {
    condition     = data.http.endpoint.status_code == 200
    error_message = "WARNING: Web application health check returned non-200 status code!"
  }
}
```

### 4. Declarative State Removal with `removed` Blocks (`removed.tf`)
```hcl
# Forget resource from state tracking WITHOUT running cloud API destroy
removed {
  from = aws_instance.legacy_server

  lifecycle {
    destroy = false # Do NOT delete actual EC2 instance
  }
}
```

### 5. Remote Module Version Pinning (`main.tf`)
```hcl
module "web_cluster" {
  # Double slash (//) specifies subfolder path inside remote repository
  source = "github.com/my-org/terraform-modules//services/web-cluster?ref=v2.1.0"

  cluster_name = "prod-web"
  min_size     = 3
  max_size     = 10
}
```

## Production Release Workflow

```
1. Feature Branch   → Implement HCL changes locally
2. Local Formatting → Run `terraform fmt -check` and `terraform validate`
3. Semantic Tagging → Release Git tag (e.g. `git tag -a v1.3.0 -m "Add HTTPS listener"`)
4. Push Release     → `git push origin v1.3.0`
5. Root Upgrade     → Update root module to `?ref=v1.3.0`
6. Init Upgrade     → Run `terraform init -upgrade` to refresh `.terraform.lock.hcl`
7. CI Plan Approval → Verify plan artifact and merge PR
```

---

## Anti-patterns

- **Using Mutable Git Branches for Module Sources (`?ref=main`)**:
  - *Why it fails*: Unvetted commits to `main` instantly propagate to live environments during the next `terraform apply`, causing accidental downtime. Always pin to immutable tags (`?ref=v1.2.0`).
- **Ignoring `.terraform.lock.hcl` in `.gitignore`**:
  - *Why it fails*: Teammates and CI pipelines download different provider minor versions, causing non-deterministic diffs and syntax breakages.
- **Performing Manual `terraform state mv` or `terraform state rm` Commands**:
  - *Why it fails*: Manual state commands leave no code record, cannot be peer-reviewed in PRs, and fail silently when executed on teammates' machines. Use `moved` and `removed` blocks in HCL.

---

## Key Takeaways

1. **Use `moved` Blocks for Refactoring**: Never run manual `terraform state mv` commands; check `moved {}` blocks into version control.
2. **Use `import` Blocks for Existing Infra**: Import brownfield assets declaratively and auto-generate HCL code using `-generate-config-out`.
3. **Commit `.terraform.lock.hcl`**: Lock provider binary checksums across all developer environments.
4. **Pin Remote Modules to Git Tags**: Always append `?ref=vX.Y.Z` to remote module source URLs.
