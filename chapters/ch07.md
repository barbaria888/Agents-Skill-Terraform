# Chapter 7 — Working with Multiple Providers, Regions, and Accounts

## Core Idea
Real-world enterprise architecture spans multiple cloud regions (disaster recovery, global delivery), multiple cloud accounts (sandbox, staging, prod account isolation), and multiple cloud providers (AWS + GCP + Kubernetes). Terraform manages multi-region, multi-account, and multi-cloud setups using provider `alias` attributes, IAM AssumeRole configurations, explicit module provider mapping, and cross-provider resource orchestration.

---

## Frameworks Introduced

### 1. The Provider Alias Framework
- **Default Provider**: Declared without an `alias`. Applied automatically to all resources of that provider type.
- **Aliased Provider**: Declared with an `alias` attribute (e.g. `alias = "west"`). Referenced explicitly on resource blocks via `provider = aws.west`.

### 2. Multi-Account AssumeRole Framework
- Instead of managing static credentials for multiple AWS accounts, define a primary credentials provider (management account) and use `assume_role` blocks in aliased provider configurations to dynamically assume target account IAM roles (`StagingDevOpsRole`, `ProdDevOpsRole`).

### 3. Module Provider Inheritance Framework
- Child modules inherit default providers automatically.
- **Aliased Providers inside Modules**: When a child module requires multiple providers or aliased providers, the child module MUST declare `configuration_aliases = [aws.primary, aws.replica]` in its `required_providers` block, and the root module MUST explicitly map them in the `providers = {}` block when calling the module.

## Code Examples

### 1. Multi-Region Deployment (`multi_region.tf`)
```hcl
# Default Provider (Primary Region: US East)
provider "aws" {
  region = "us-east-1"
}

# Aliased Provider (Secondary Region: US West)
provider "aws" {
  alias  = "west"
  region = "us-west-2"
}

# Resource in Primary Region
resource "aws_vpc" "primary" {
  cidr_block           = "10.1.0.0/16"
  enable_dns_hostnames = true

  tags = {
    Name = "primary-vpc-east"
  }
}

# Resource in Secondary Region (Explicit Provider Reference)
resource "aws_vpc" "secondary" {
  provider             = aws.west
  cidr_block           = "10.2.0.0/16"
  enable_dns_hostnames = true

  tags = {
    Name = "secondary-vpc-west"
  }
}
```

### 2. Multi-Account Setup with IAM AssumeRole (`multi_account.tf`)
```hcl
# Management Account Provider
provider "aws" {
  region = "us-east-1"
}

# Staging Account Provider via AssumeRole
provider "aws" {
  alias  = "staging"
  region = "us-east-1"

  assume_role {
    role_arn     = "arn:aws:iam::111111111111:role/TerraformDeploymentRole"
    session_name = "terraform-staging-session"
  }
}

# Production Account Provider via AssumeRole
provider "aws" {
  alias  = "prod"
  region = "us-east-1"

  assume_role {
    role_arn     = "arn:aws:iam::222222222222:role/TerraformDeploymentRole"
    session_name = "terraform-prod-session"
  }
}

# Deploying Database in Staging Account
resource "aws_db_instance" "staging_db" {
  provider           = aws.staging
  identifier_prefix  = "stage-db-"
  engine             = "postgres"
  allocated_storage  = 20
  instance_class     = "db.t3.micro"
  username           = "dbuser"
  password           = var.staging_db_password
}

# Deploying Database in Production Account
resource "aws_db_instance" "prod_db" {
  provider           = aws.prod
  identifier_prefix  = "prod-db-"
  engine             = "postgres"
  allocated_storage  = 100
  instance_class     = "db.r6g.large"
  username           = "dbuser"
  password           = var.prod_db_password
}
```

### 3. Passing Providers to Child Modules Worked Example

#### Child Module Definition (`modules/multi-region-s3/main.tf`)
```hcl
terraform {
  required_providers {
    aws = {
      source                = "hashicorp/aws"
      version               = "~> 5.0"
      configuration_aliases = [aws.primary, aws.replica] # Required provider aliases
    }
  }
}

resource "aws_s3_bucket" "primary" {
  provider = aws.primary
  bucket   = var.primary_bucket_name
}

resource "aws_s3_bucket" "replica" {
  provider = aws.replica
  bucket   = var.replica_bucket_name
}
```

#### Root Module Invocation (`main.tf`)
```hcl
provider "aws" {
  alias  = "east"
  region = "us-east-1"
}

provider "aws" {
  alias  = "west"
  region = "us-west-2"
}

module "cross_region_s3" {
  source = "./modules/multi-region-s3"

  # Pass providers explicitly to match child configuration_aliases
  providers = {
    aws.primary = aws.east
    aws.replica = aws.west
  }

  primary_bucket_name = "my-company-primary-storage-east"
  replica_bucket_name = "my-company-replica-storage-west"
}
```

### 4. Multi-Cloud / Cross-Provider Orchestration (AWS RDS + Kubernetes Secret)
```hcl
provider "aws" {
  region = "us-east-1"
}

provider "kubernetes" {
  config_path = "~/.kube/config"
}

# Create AWS Database
resource "aws_db_instance" "postgres" {
  identifier_prefix   = "k8s-app-db-"
  engine              = "postgres"
  allocated_storage   = 20
  instance_class      = "db.t3.micro"
  username            = "appuser"
  password            = var.db_password
  skip_final_snapshot = true
}

# Inject AWS Database Endpoint Directly into Kubernetes Cluster Secret
resource "kubernetes_secret" "db_credentials" {
  metadata {
    name      = "db-credentials"
    namespace = "default"
  }

  data = {
    DB_HOST = aws_db_instance.postgres.address
    DB_PORT = tostring(aws_db_instance.postgres.port)
    DB_USER = aws_db_instance.postgres.username
    DB_PASS = var.db_password
  }
}
```

## Anti-patterns

- **Hardcoding Account AWS Credentials in Provider Blocks**:
  - *Why it fails*: Exposes secret access keys in source code. Use `assume_role` or environment credentials.
- **Assuming Child Modules Inherit Aliased Providers Automatically**:
  - *Why it fails*: Child modules ONLY inherit default un-aliased providers. If a child module uses aliased providers without `configuration_aliases` and explicit caller mapping, `terraform plan` fails.
- **Combining Dynamic Data Providers with Resource Creation in a Single Run**:
  - *Why it fails*: Creating an EKS cluster and configuring the `kubernetes` provider with data outputs from that EKS cluster in the *same* HCL run can cause provider initialization failures during `terraform init`/`plan`. **Fix**: Split cluster creation and K8s object deployment into separate state directories.

---

## Key Takeaways

1. **Use Provider Aliases for Multi-Region**: Define `alias` attributes for alternate regions and reference via `provider = aws.alias_name`.
2. **Use AssumeRole for Multi-Account**: Authenticate centrally and assume target account IAM roles dynamically.
3. **Declare `configuration_aliases` in Modules**: Require explicit caller provider mapping when building multi-region/account child modules.
4. **Isolate Cluster Creation from Workload Provisioning**: Keep Kubernetes/Helm resource definitions in a separate state file from the EKS/GKE cluster creation code.
