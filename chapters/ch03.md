# Chapter 3 — How to Manage Terraform State

## Core Idea
Terraform state (`terraform.tfstate`) is the single source of truth mapping your code to real-world infrastructure assets. In team environments, local state files cause severe state divergence, concurrent edit corruption, and credential leakage. Production state must be stored in a remote backend with encryption at rest, access logging, and atomic state locking (e.g., S3 + DynamoDB).

---

## Frameworks Introduced

### 1. The Remote State Backend Architecture (S3 + DynamoDB)
- **S3 Bucket**: Hosts the JSON state file remotely. Requires bucket versioning (for rollback) and server-side encryption (`AES256` or AWS KMS).
- **DynamoDB Table**: Provides atomic state locking via a single primary key named `LockID` (type string). Prevents concurrent `terraform apply` executions from corrupting state.
- **Backend Configuration**: A `backend "s3"` block inside the `terraform {}` block that specifies `bucket`, `key`, `region`, `dynamodb_table`, and `encrypt = true`.

### 2. The 2 State Isolation Frameworks
- **Workspaces (Avoid for Production Environment Isolation)**:
  - *How it works*: Single code directory storing parallel state files under different workspace names in the same backend key path.
  - *Trade-off*: Low file separation; identical authentication permissions; easy to accidentally run `apply` against production when sitting in `dev` workspace context.
- **Directory File Layout (Recommended Production Standard)**:
  - *How it works*: Isolate environments (`stage`, `prod`, `global`) and infrastructure components (`vpc`, `db`, `services`) into separate, nested physical subdirectories.
  - *Trade-off*: Each directory has its own isolated state file, backend configuration, and RBAC IAM policy; minimizes blast radius.

### 3. Remote State Inter-Module Communication (`terraform_remote_state`)
- When state is isolated into separate directory trees, modules cannot directly reference each other's resources.
- Use `data "terraform_remote_state"` to read **outputs** exported by another state file in a read-only manner.

## Code Examples

### 1. Bootstrapping the Remote Backend Infrastructure (`global/s3/main.tf`)
```hcl
provider "aws" {
  region = "us-east-2"
}

# S3 Bucket for State Storage
resource "aws_s3_bucket" "terraform_state" {
  bucket        = "my-company-tf-state-prod"
  force_destroy = false # Prevent accidental bucket destruction

  lifecycle {
    prevent_destroy = true
  }
}

# Enable S3 Versioning for Rollbacks
resource "aws_s3_bucket_versioning" "enabled" {
  bucket = aws_s3_bucket.terraform_state.id
  versioning_configuration {
    status = "Enabled"
  }
}

# Server-Side Encryption by Default
resource "aws_s3_bucket_server_side_encryption_configuration" "default" {
  bucket = aws_s3_bucket.terraform_state.id

  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm = "AES256"
    }
  }
}

# Block Public Access to Bucket
resource "aws_s3_bucket_public_access_block" "public_access" {
  bucket                  = aws_s3_bucket.terraform_state.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# DynamoDB Table for Distributed State Locking
resource "aws_dynamodb_table" "terraform_locks" {
  name         = "my-company-tf-locks-prod"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "LockID" # MUST be exactly LockID

  attribute {
    name = "LockID"
    type = "S"
  }
}
```

### 2. Configuring the Backend in Application Components (`stage/services/web-cluster/main.tf`)
```hcl
terraform {
  required_version = ">= 1.5.0"

  backend "s3" {
    bucket         = "my-company-tf-state-prod"
    key            = "stage/services/web-cluster/terraform.tfstate"
    region         = "us-east-2"
    dynamodb_table = "my-company-tf-locks-prod"
    encrypt        = true
  }
}
```

### 3. Reading Remote State Outputs (`stage/services/web-cluster/data.tf`)
```hcl
# Read Database Endpoint from the Data-Store Component State
data "terraform_remote_state" "db" {
  backend = "s3"

  config = {
    bucket = "my-company-tf-state-prod"
    key    = "stage/data-stores/mysql/terraform.tfstate"
    region = "us-east-2"
  }
}

# Reference Remote Output inside Application Config
resource "aws_launch_template" "example" {
  name_prefix = "web-lt-"

  user_data = base64encode(templatefile("${path.module}/user_data.sh.tpl", {
    db_address = data.terraform_remote_state.db.outputs.address
    db_port    = data.terraform_remote_state.db.outputs.port
  }))
}
```

## Recommended Directory File Layout

```
live/
├── global/
│   ├── s3-backend/          # S3 Bucket & DynamoDB Lock Table
│   └── iam/                 # Global Roles & Groups
├── stage/
│   ├── vpc/                 # Networking (VPC, Subnets, Gateways)
│   ├── data-stores/
│   │   └── mysql/           # Database layer
│   └── services/
│       └── web-cluster/     # Compute layer (ALB + ASG)
└── prod/
    ├── vpc/
    ├── data-stores/
    │   └── mysql/
    └── services/
        └── web-cluster/
```

## Anti-patterns

- **Storing State Files in Git Repositories**:
  - *Why it fails*: Exposes secrets stored in plain-text state JSON; leads to git merge conflicts and corrupted state files.
- **Single Giant Root Module / Monolithic State**:
  - *Why it fails*: Entire infrastructure shares a single state file. A typo in web configuration can delete production databases (`blast radius = infinity`). Slow `plan`/`apply` execution times.
- **Using Workspaces for Prod/Stage Isolation**:
  - *Why it fails*: Workspaces use the same authentication permissions and directory tree. A developer typing `terraform apply` without checking `terraform workspace show` can accidentally apply dev changes to prod.

---

## Key Takeaways

1. **State is Sacred**: Never edit state JSON manually. Use `terraform state` CLI commands (`mv`, `rm`, `list`, `show`).
2. **Locking is Mandatory**: Always attach a DynamoDB table to your S3 backend configuration to prevent race conditions.
3. **Isolate by Directory**: Separate `dev`, `stage`, and `prod` into isolated directory trees with distinct S3 key paths and IAM permissions.
4. **Minimize Blast Radius**: Break large infrastructure into isolated state layers (`vpc`, `database`, `compute`).
