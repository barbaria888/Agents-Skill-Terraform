# Chapter 10 — How to Use Terraform as a Team

## Core Idea
Scaling Terraform across engineering teams requires establishing automated version-controlled pull request workflows, zero-trust credential handling (OIDC), state locking during code review, policy-as-code enforcement (Sentinel / OPA), and automated GitOps deployment pipelines (Atlantis, HCP Terraform, GitHub Actions).

---

## Frameworks Introduced

### 1. The 7-Step Team Infrastructure PR Workflow
```
1. Developer Feature Branch  → Pull branch from `main`
2. Local Pre-flight Check    → Run `terraform fmt -check` and `tflint`
3. Push Branch & Open PR     → Triggers automated CI workflow
4. Automated Speculative Plan→ CI/Atlantis executes `terraform plan -out=tfplan`
5. Peer Code & Plan Review   → Team verifies HCL logic and precise diff output
6. Merge to Main Branch      → Triggers automated CD apply
7. Automated Apply           → CD pipeline applies ONLY the saved `tfplan` artifact
```

### 2. The 3 Team Automation Architectures

| Tool / Platform | Architecture | How Plan / Apply Executes | Access Control & State |
|---|---|---|---|
| **GitOps PR Bot (Atlantis)** | Open-source server listening to Git webhooks | Executed inside Atlantis worker via PR comments (`atlantis plan`, `atlantis apply`) | Locks state per PR; developers never handle cloud credentials |
| **Managed SaaS (HCP Terraform)** | Cloud-hosted platform (HashiCorp) | Automatic speculative runs on VCS push; web UI approval gates | Remote state hosting, Sentinel/OPA policies, Private Module Registry |
| **Custom CI/CD (GitHub Actions / GitLab CI)** | Containerized CI runners | CLI execution using OIDC cloud authentication | State stored in S3/DynamoDB; saved `tfplan` artifacts passed between jobs |

### 3. The Policy-as-Code Governance Framework (Sentinel / OPA)
- Enforces organizational compliance, security rules, and cost guardrails **before** `terraform apply` executes.
- *Examples*: "Do not allow public S3 buckets", "EC2 instance types must be `t3.*` or `m6g.*`", "All resources must have `Environment` and `Owner` tags".

## Code Examples

### 1. OIDC Authentication Setup in GitHub Actions (`.github/workflows/terraform.yml`)
```yaml
name: "Terraform Team Pipeline"

on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]

permissions:
  id-token: write # Required for requesting the OIDC JWT
  contents: read
  pull-requests: write

jobs:
  terraform:
    name: "Terraform Plan & Apply"
    runs-on: ubuntu-latest

    steps:
    - name: Checkout Code
      uses: actions/checkout@v3

    # Authenticate with AWS via OIDC (No static credentials stored in GitHub Secrets!)
    - name: Configure AWS Credentials via OIDC
      uses: aws-actions/configure-aws-credentials@v2
      with:
        role-to-assume: arn:aws:iam::123456789012:role/GitHubActionsTerraformRole
        aws-region: us-east-1

    - name: Setup Terraform
      uses: hashicorp/setup-terraform@v2
      with:
        terraform_version: 1.6.0

    - name: Terraform Format Check
      run: terraform fmt -check

    - name: Terraform Init
      run: terraform init

    # Speculative Plan on Pull Request
    - name: Terraform Plan
      id: plan
      if: github.event_name == 'pull_request'
      run: terraform plan -no-color -out=tfplan

    # Save Plan Artifact to prevent race conditions during apply
    - name: Upload Plan Artifact
      if: github.event_name == 'pull_request'
      uses: actions/upload-artifact@v3
      with:
        name: tfplan
        path: tfplan

    # Apply ONLY on Merge to Main
    - name: Terraform Apply
      if: github.ref == 'refs/heads/main' && github.event_name == 'push'
      run: terraform apply -auto-approve tfplan
```

### 2. Atlantis GitOps Configuration (`atlantis.yaml`)
```yaml
version: 3
automerge: true
delete_source_branch_on_merge: true
projects:
- name: stage-web-cluster
  dir: stage/services/web-cluster
  workspace: default
  terraform_version: v1.6.0
  autoplan:
    when_modified: ["*.tf", "../../../modules/**/*.tf"]
    enabled: true
  apply_requirements: [approved, mergeable]
```

### 3. Open Policy Agent (OPA) Rule for Tagging (`policy/tags.rego`)
```rego
package terraform.analysis

default allow = false

# Ensure all created AWS resources have an Environment tag
allow {
    resource := input.resource_changes[_]
    resource.change.actions[_] == "create"
    resource.change.after.tags.Environment != null
}
```

## Anti-patterns

- **Running `terraform apply` from Local Developer Laptops**:
  - *Why it fails*: Creates unvetted infrastructure changes, bypasses peer code review, risks applying uncommitted local code, and requires distributing admin cloud credentials to developer laptops.
- **Storing Static AWS Access Keys in CI/CD Secrets**:
  - *Why it fails*: Static long-lived API keys leak easily and are difficult to rotate. Use OIDC (OpenID Connect) for dynamic, short-lived session tokens.
- **Applying Without Saved Plan Artifacts (`terraform apply` vs `terraform apply tfplan`)**:
  - *Why it fails*: Running `terraform apply` directly in CD re-evaluates the plan at apply time. If cloud resources changed between PR approval and merge, unexpected destructions occur. Always apply saved `tfplan` artifacts.

---

## Key Takeaways

1. **Automate Plan & Apply in CI/CD**: Move execution off local machines to GitOps tools (Atlantis, HCP Terraform, GitHub Actions).
2. **Never Pass Static Cloud Keys**: Use OIDC for credential-free CI/CD execution.
3. **Always Apply Saved Plans**: `terraform plan -out=tfplan` -> `terraform apply tfplan`.
4. **Enforce Policy-as-Code**: Use OPA or Sentinel to catch security and tagging compliance issues before apply.
