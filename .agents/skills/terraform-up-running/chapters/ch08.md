# Chapter 8 — Production-Grade Terraform Modules: Versioning and Releases

In production, modules should be version-controlled and pinned to specific, immutable release tags to prevent code changes from unexpectedly breaking live environments.

## 1. Local vs. Remote Module Paths

During initial development, local paths (`source = "../../modules/web-cluster"`) are preferred because changes are applied instantly. However, for production layouts, you should reference modules from a remote repository pinned to a version:

```hcl
module "web_cluster" {
  # Double slash (//) specifies the subdirectory path inside the repository
  source = "github.com/my-company/terraform-modules//services/web-cluster?ref=v1.2.0"

  cluster_name = "prod-web"
  # ...
}
```

## 2. Versioning Repositories

There are two common layouts for storing reusable modules:

### Layout A: Monorepo (One Repo, Many Modules)
All modules reside in a single repository.

- **Pros**: Easy to search, manage, and update across modules in a single PR.
- **Cons**: Version tags apply to the *entire* repo. A tag `v1.2.0` updates all modules in the repo.
- **Source URL**: `github.com/org/repo-name//modules/my-module?ref=v1.2.0`

### Layout B: Multi-Repo (One Repo Per Module)
Every module has its own dedicated repository.

- **Pros**: Clean semantic versioning per module.
- **Cons**: High management overhead. Upgrading multiple modules requires managing multiple pull requests.
- **Source URL**: `github.com/org/terraform-aws-my-module?ref=v1.0.3`

## 3. Creating & Releasing Module Versions

For remote versioning, follow these steps to release a change:

1. **Write Code**: Implement your changes and commit to `main`.
2. **Tag Release**: Create a Git tag representing a semantic version.
   ```bash
   git tag -a v1.2.0 -m "Release version 1.2.0 with health check updates"
   git push origin v1.2.0
   ```
3. **Verify and Pin**: Update root configurations to use `?ref=v1.2.0`. Run `terraform init -upgrade` to download the new version.

## 4. Module Registries

### Terraform Registry
The public Terraform Registry requires module names to follow the naming convention `terraform-<PROVIDER>-<NAME>`.

### Private Registries
Enterprise teams can use:
- **Terraform Cloud / Enterprise Private Registry**
- **Git Provider Registries** (e.g. GitLab Package Registry)
- **Generic S3 / GCS Buckets**

Example using a Terraform Cloud private registry:
```hcl
module "vpc" {
  source  = "app.terraform.io/my-company/vpc/aws"
  version = "1.2.0" # Clean version parameters (no ?ref= required)
}
```
