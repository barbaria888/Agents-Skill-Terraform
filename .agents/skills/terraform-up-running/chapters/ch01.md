# Chapter 1 — Why Terraform?

## IaC Categories

| Category | Tools | How it Works | Key Trait |
|---|---|---|---|
| Ad hoc scripts | Bash, Python | Manual custom scripts | No state, no idempotency |
| Configuration management | Ansible, Chef, Puppet, SaltStack | Install/configure software on existing servers | Mutable infra, procedural |
| Server templating | Packer, Docker, Vagrant | Bake immutable images (AMI, container) | Immutable artifacts |
| Orchestration | Kubernetes, ECS, Nomad | Deploy & manage containers/services | Scheduling, self-healing |
| **Provisioning** | **Terraform, Pulumi, CloudFormation** | **Create the infra itself** | **Declarative, stateful** |

## Terraform vs Alternatives

| Tool | Type | Language | State | Multi-Cloud | Notes |
|---|---|---|---|---|---|
| **Terraform** | Provisioning | HCL (declarative) | Yes (local or remote) | ✅ First-class | Open source + Terraform Cloud |
| CloudFormation | Provisioning | JSON/YAML | Yes (AWS-managed) | ❌ AWS only | Deep AWS integration |
| Pulumi | Provisioning | TypeScript/Python/Go | Yes | ✅ | Code, not config |
| Ansible | Config mgmt | YAML (procedural) | Partial | ✅ | Great for config, weak for infra |
| CDK/CDKTF | Provisioning | TS/Python wrapping TF | Yes | ✅ | Code → HCL → Terraform |

## Terraform Benefits

- **Declarative** — describe desired end state, not steps
- **Idempotent** — apply multiple times = same result
- **Plan** — preview changes before applying
- **State** — knows what it manages (vs. what already exists)
- **Multi-cloud** — AWS, GCP, Azure, and 3,000+ providers
- **Community** — Terraform Registry has thousands of modules

## Key Design Decisions

### Procedural vs Declarative
- Procedural (Ansible): describe the steps → can break if run twice
- Declarative (Terraform): describe the goal → handles idempotency for you

### Mutable vs Immutable Infrastructure
- Mutable: patch servers in place (config drift over time)
- **Immutable**: replace servers with new image on every change (Terraform + Packer approach — recommended)

### Master vs Masterless
- Chef/Puppet: master server required (ops overhead, SPOF)
- **Terraform: masterless** — runs locally or in CI, no server to manage

### Agent vs Agentless
- Chef/Puppet: agents on every server (overhead, security surface)
- **Terraform: agentless** — uses cloud provider APIs directly
