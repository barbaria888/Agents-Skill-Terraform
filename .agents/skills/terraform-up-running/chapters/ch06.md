# Chapter 6 — Production-Grade Terraform: Infrastructure is Code

Production-grade infrastructure is defined not just by deployment, but by how it is managed, maintained, and operated over time.

## 1. Pillars of Production-Grade Infrastructure

| Pillar | Description | Key Practices |
|---|---|---|
| **Reliability** | Minimizing downtime and faults. | Multi-region, backups, self-healing, automated failover, load balancing. |
| **Security** | Zero-trust access. | Encryption at rest and in transit, IAM roles, least privilege, Secret Manager. |
| **Manageability** | Clear organization and simple updates. | Small modules, declarative code, peer-reviewed pull requests. |
| **Observability** | Visibility into state and behavior. | Metrics, distributed tracing, structured logging, alarms. |
| **Cost** | Minimizing resource waste. | Auto-scaling, tag-based cost allocation, clean up unused resources. |

## 2. Module Sizing & Design

Avoid the "one giant module" anti-pattern. Instead, structure your modules around a single, specific responsibility.

```
                  ┌──────────────────┐
                  │   Root Module    │
                  │   (Live/Stage)   │
                  └────────┬─────────┘
                           │
         ┌─────────────────┼─────────────────┐
         ▼                 ▼                 ▼
┌────────────────┐┌────────────────┐┌────────────────┐
│   VPC Module   ││   DB Module    ││  Web Cluster   │
│                ││                ││     Module     │
└────────────────┘└────────────────┘└────────────────┘
```

### Key Principles:
1. **Low Coupling**: A change to the web-server module should not impact or require updating the VPC module.
2. **High Cohesion**: Keep resources that share a lifecycle together (e.g. ALB, target groups, and listener rules are tightly coupled and belong in the same module).
3. **Module Composition**: Build complex environments by combining small modules together in a root configuration, passing outputs from one as inputs to another.

## 3. Storing State Safely

- **Isolate by Environment**: Use different AWS accounts/GCP projects for `dev`, `stage`, and `prod` to prevent cross-environment accidents.
- **Isolate by Component**: Within each environment, separate state files for layers of infrastructure (e.g., separate states for `vpc`, `data-stores`, and `app-services`).
- **Permissions**: Grant write access to production state buckets only to the CI/CD pipeline, never directly to developers.

## 4. Operational Runbooks & CI/CD

All infrastructure changes should run through a standardized pipeline:

```
Developer makes PR  →  CI Runs Tests  →  Peer Review  →  Merge to main  →  CD Applies Change
                        - validate                      - check plan               - apply plan
                        - lint/fmt                      - approve diff             - verify output
                        - dry-run plan
```

### Automation Best Practices:
1. **Pin Versions**: Pin Terraform version, providers, and modules.
2. **Review the Plan**: Build step must save the `plan` output as an artifact (`terraform plan -out=tfplan`), and the deploy step must apply *only* that specific plan (`terraform apply tfplan`).
3. **Use OIDC**: Do not store long-lived credentials in CI/CD secrets. Use OpenID Connect (OIDC) to authenticate your runner directly with your cloud provider dynamically.
